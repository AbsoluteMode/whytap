## Context

Presentation amendment on 2026-10-21: the [Calendar in Hover decision](2026-10-21-calendar-hover.md)
supersedes the window entry below. Local storage/provider architecture remains;
normal Calendar and To-do entry points, including Toolbox, now open Hover.

The user requested a local To-do list, then extended it with Whytap's own
calendar and a common view of Google, Apple, Outlook, Teams and Zoom calendars.
They selected direct provider connections inside Whytap rather than requiring
Google, Outlook and Zoom to be registered in macOS first.

## Alternatives

- Use only macOS calendar accounts through EventKit: fewer provider integrations,
  but does not satisfy the selected direct Google/Microsoft/Zoom connection flow.
- Add an Whytap synchronization backend: not selected; conflicts with the
  application's existing no-owned-backend boundary.

## Decision

Calendar opens the native Planner window. The original shared-window To-do
entry was superseded on 2026-10-20 by [compact To-do in hover](2026-10-20-todo-hover.md);
existing tool layouts and task data are preserved. Keep local task/event data in an
atomic private archive, and keep provider credentials in Keychain. Use EventKit
for calendars available on the Mac; use direct browser OAuth with PKCE for
Google Calendar, Microsoft Graph and Zoom Calendar Service.

The implemented first version edits local events and reads external calendars.
Remote recurrence is expanded within the visible range by the provider. It
refreshes while the calendar view is visible, handles per-account failure, and
collapses copies only when external UID and occurrence boundaries match.

## Rationale

A common native window provides enough space for the month and daily agenda,
while the island remains the entry point. The local calendar and task list work
without provider registration or network access. Direct native OAuth avoids
introducing an application backend or embedding a confidential server secret.
External data is never copied into the user's local Whytap calendar automatically.

Short-lived access tokens stay in the OAuth actor's memory. Only refresh tokens
and native client configuration are persisted and backed up. An access-only
refresh must not change settings history or trigger a full archive upload;
rotated refresh tokens still persist before the next API request. Rotation alone
also does not create a settings version or full archive: hourly credential churn
must not displace meaningful rollback points or repeatedly upload meeting audio.
The settings comparison ignores rotation only for a validated calendar credential
with the same account/client; API keys, client changes, additions and removals keep
normal change detection. The next real snapshot or archive includes current
refresh tokens. Restoring an older token can require reconnecting, particularly
when a provider invalidates previous tokens. The decoder
accepts the earlier credential shape, while newly restored authorization obtains
a fresh access token on first use.

## Sources

The user requirement and implementation entry points are listed in frontmatter.
[Microsoft refresh-token rotation](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)
and [Zoom OAuth](https://developers.zoom.us/docs/integrations/oauth/) require keeping
the latest refresh token; they do not make a historical backup a guaranteed login.
[The guide](../../docs/planner.md) records the exact provider contracts and setup
references checked during implementation.

## Comments and objections

No user objection was recorded. The read-only external-event scope is the
implementation's initial boundary, not a user request to prohibit future editing.

## Resolution

The source implements local tasks/events and native/direct calendar adapters.
The owner must supply registered native OAuth client configuration at packaging. Live provider consent,
account compatibility and installed-app interaction remain separate acceptance
steps; synthetic tests do not establish those results.

## Consequences

Google, Microsoft and Zoom require registered public OAuth clients before live
sign-in. Zoom Calendar Service differs from a Zoom client's linked Google or
Microsoft calendar; the latter uses its actual provider connection. Teams links
arrive from Outlook events. The local archive is a new data store. Encrypted backups now include local Planner content, selected-calendar settings
and saved account credentials. Restore validates the bounded local archive before
replacement and retains previous bytes in its durable rollback journal. Older
settings archives preserve existing calendar connection keys. Account registrations
and live sign-in are external acceptance, not evidence inferred from fixture tests.
