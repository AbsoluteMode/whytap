# To-do tree

## Context

To-do was a flat list. Research and follow-up work after calls needs a parent
task with steps under it and a visible progress note per step, written by the
user or by coding agents.

## Decision

- A task may have `parentID` (another task) and `status` (one line, up to 300
  characters). Depth is at most five levels. Both fields are optional and are
  omitted from the file when unset, so flat archives keep their exact shape.
- Closing a task closes all its open descendants with the same timestamp.
  Reopening reopens the descendants closed together with it (not ones closed
  earlier on their own) and any closed ancestors, so the task is visible.
- Hover To-do shows the tree: indentation, a disclosure chevron with a count
  when collapsed (collapse state lives for the app session), the status under the
  title after a branch glyph, and titles up to two lines. A hover "+" adds a
  subtask inline; the row context menu adds Add Subtask, Add/Edit Status, Rename
  and Complete/Reopen. Return commits, Escape cancels, an empty status clears it.
  History lists closed tasks with their parent's title. Hovering a row whose
  title or status is cut off shows its full text in a bubble left of the
  drawer, like the History preview (user feedback the same day).
- `TodoRequest`/`TodoTree` in WhytapCaseKit are the single rule set: the app
  (`PlannerStore.editTasks`), the helper's closed-app file path and the MCP tools
  apply the same validation and changes. `whytap todo` adds `--parent`,
  `--status`, `--json` trees, `set` (title, status, parent), `done` and `reopen`;
  MCP adds `whytap_todo_update` and tree input to `whytap_todo_add`. IDs accept a
  unique 8+ character prefix. A flat batch is still sent as `titles`, so an older
  running app accepts it.
- An active sibling with the same title is reused (its given status applied), so
  repeating an agent's tree never duplicates it.

## Why

Parent/child links in the existing task list keep one archive, one backup
section and one lock; a separate notes or subtask store would need its own
merge rules. Cascading close matches the user's request and avoids orphaned
open steps under a finished task. A one-line status keeps the narrow island
readable; longer notes belong in the meeting note itself. Sharing one
request type removes the risk of the app and the helper disagreeing, the bug
class the builder caught in ticket 181.

## What was tested

Tree add from JSON (the user's example) with statuses and depth order, retry
without duplicates and status refresh, add under a prefix id from stdin and
with --status, cascading close and selective reopen, reopen of a subtask
reopening its parents, edits of every field, refusals (cycle, self, not found,
six levels when adding or moving, parent closed, status too long, malformed
JSON, unknown keys) without contacting the app or writing the file, flat batches
still sent as titles, an older app's refusal never falling back to the file,
unknown fields and stored numbers kept in closed-app edits, validator rejection
of missing parents/cycles/self/blank or long statuses/six levels, the app and a
fresh launch reading the same tree, hover collapse, inline subtask/status/rename
with validation, agent updates while the panel is open, and offscreen renders at
310/360 pt. Not tested: the installed app, real pointer/keyboard focus.

## Rejected

- Separate subtask list per task: two places to edit and merge.
- Multi-line or rich-text statuses: unreadable in the 310 pt island.
- Unlimited depth: indentation would leave no room for titles.
- Closing a parent while leaving children open: the user asked for children to leave with it.
- Deleting subtrees from hover or agents: not requested; destructive.

Rollback: an older build loads tree archives (it ignores the new fields) but
flattens them when it saves.
