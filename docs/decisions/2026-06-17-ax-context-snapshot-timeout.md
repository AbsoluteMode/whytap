# AX-контекст для дропа: общий wall-clock таймаут на обход

## Контекст

Прод-баг «synking»: после короткой диктовки (напр. «Привет») текст вставляется,
но Dynamic Island застревает на «thinking…» на ~55 секунд, потом турн
доезжает. У разработчика (Максим) не воспроизводится — только у части
пользователей.

Разбор по prod-логам (`sidekey-backend-app-1`, user_id=10, build 1.9.2):

```
08:04:47.2  voice_turn_started
08:04:47.5  WebSocket STT открыт
08:04:50.1  connection closed        ← запись «Привет» = 2.6с, штатно
            ▼ 55.8с тишины в backend ▼
08:05:45.9  POST /api/process        latency_ms=1, fast_skip
08:05:46.5  paste_completed
```

Ключевые факты, отсекшие ложные следы:
- `/api/process` сам = **1 мс** → backend ни при чём.
- В окне дыры (53с) backend увидел **ровно одну** строку → клиент **не ходил
  в сеть**, был занят локально.
- paste произошёл → результат сессии был `.transcript` → `finished` пришёл →
  WS дожил → сеть/VPN ни при чём (в отличие от отдельного бага A у VPN-юзеров).

Единственный длинный `await` между `resolve(.transcript)` и `/api/process` —
`AXContextReader.snapshot(forPID:)`: читает текст активного окна целевого
приложения через Accessibility, чтобы отдать smart-клинеру как контекст.

## Решение

Добавить **общий wall-clock таймаут** (`defaultWalkTimeout = 1.5с`) на весь
AX-обход в `AXContextReader.snapshot(forPID:)`. Обход гоняется в
`Task.detached`; по истечении таймаута задача `cancel()`-ится, а `liveCollect`
проверяет `Task.isCancelled` на каждом узле и прекращает спуск. На таймауте
контекст отбрасывается (как для web-приложений, которые и так ничего не
отдают), и вставка идёт без него.

## Почему

У обхода были только две защиты, и **обе одномерные**:
- `AXUIElementSetMessagingTimeout(app, 0.5)` — лимит на **одно** сообщение;
- `budget = 600` — лимит на **число** узлов.

Их произведение — минуты: 600 узлов × ~4 AX-вызова × до 0.5с. На приложении,
медленно отвечающем на Accessibility (глубокое дерево / тормозящее окно),
обход реально занимает десятки секунд. Ни per-message-таймаут, ни node-budget
не ограничивают **суммарное** стенное время — нужен отдельный потолок на весь
обход.

Контекст — best-effort («free win where it works, silent no-op where it
doesn't»), поэтому его потеря на медленном приложении безопасна: быстрые
приложения (общий случай) получают контекст как раньше, медленные перестают
вешать дроп. Таймаут — потолок, а не задержка.

## Что протестировали

- **Гипотеза «сеть/WS»** — отвергнута: paste произошёл, значит `finished`
  пришёл и WS дожил; backend молчал 53с (клиент не в сети). 55с ≈ 60с
  (дефолт `URLSession.timeoutIntervalForRequest`) оказалось совпадением, а не
  причиной.
- **Гипотеза «backend/Smart-cleaner»** — отвергнута: `/api/process`
  latency_ms=1, режим `fast_skip` (контекст в fast-режиме даже не используется).
- **Гипотеза «AX-обход без общего таймаута»** — подтверждена кодом
  (0.5с × 600 = минуты) + локализацией по логам (единственный длинный `await`
  в окне дыры, клиент локально занят).
- TDD: `test_snapshot_abandons_context_when_the_walk_exceeds_the_timeout`
  (медленный отменяемый collector → возврат за <1с, контекст отброшен);
  `test_snapshot_returns_context_when_the_walk_finishes_before_timeout`
  (быстрый путь не задет).

Временная диагностика `drop_phase_debug` (#350) при этом **удалена**, а не
починена: причину нашли без неё (по `voice_turn`-таймингам + тишине backend),
а в текущем виде она ещё и логировала `String(describing: wing)`, где
`.recording(transcript:)` сериализует **live-транскрипт** в metadata — утечка
текста диктовки на `/api/events` (нашёл Codex-ревью, нарушение инварианта #3).
Удаление снимает утечку разом и не оставляет временный код в проде.
Подтверждение AX-фикса — поведенческое (репро → не виснет); если 55с делятся
между `.verifying` (AX) и `.transcribing` (WS-финализация), вернём диагностику
уже sanitized (`wing_state` без associated value).

## Отвергли

- **withTaskGroup для гонки обхода против таймаута** — при выходе неявно ждёт
  все child-задачи, включая блокирующий синхронный обход → возврат не
  ускоряется (тест ловил полные 2с). Заменено на `await work.value` +
  отдельная таймаут-задача, шлющая `cancel()`.
- **Только node-budget поменьше** (напр. 100) — всё равно одномерно; медленные
  узлы дают секунды, а агрессивный budget рубит контекст и на быстрых
  приложениях. Wall-clock честнее отражает «сколько мы готовы ждать».
- **Совсем убрать AX-контекст из дропа** — теряем реальный выигрыш на быстрых
  нативных приложениях (Mail, Notes, …). Таймаут сохраняет выигрыш, убирая
  только хвост.
- **Не собирать AX-контекст в fast-режиме** (он там не используется —
  `fast_skip`) — валидная оптимизация, но отдельный followup; таймаут чинит
  корень для всех режимов сразу.
