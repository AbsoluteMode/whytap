# Silent auto-reconnect + autoEnd startup grace

> **Частично отменено 29 июля 2026.** Слой 2 (тихий auto-reconnect на gap
> ≤15с) удалён: он склеивал в одну запись две разные встречи при переходе
> Teams → Zoom за 7 секунд. Теперь любой re-fire внутри grace спрашивает
> пилюлей. Слой 1 (startup grace 30с) в силе — именно он закрывает
> описанный ниже инцидент. См.
> `docs/decisions/2026-07-29-reconnect-always-asks.md`.

## Контекст

Прод-репорт (20 июля, Максим): вход в Zoom-встречу, Notes на надже, Zoom
догружается — и через ~20 секунд всплывает пилюля «Notes | Reconnect after
1s | Skip». Reconnect «сработал не в тему»: пользователь никуда не выходил.

Хронология из локального store: запись стартовала 18:01:38, авто-энд в
18:01:58 (21 секунда, один WAV-чанк), через ~1 секунду детектор снова
увидел митинг и показал reconnect-нудж. Оттаймаутившийся нудж отправил
21-секундный обрывок на бэкенд — он стал «встречей» с одной фразой и
потратил секунды квоты.

Механика: Zoom при подключении к конференции флапает микрофон (prejoin
preview → release → conference audio re-acquire), release длится > 3
секунд. `MeetingRecorder`'s auto-end watcher (порог
`autoEndMicReleasedSeconds = 3`) убил запись; детектор тем же порогом
завёл новую сессию; свежий `pendingReconnect` (grace 3 мин) дал
`.suggestingReconnect`. Каждый слой отработал «по инструкции» — ложным
был сам авто-энд на секундах жизни записи. Route-change-резилиентность
1.18.2 (PR #526, generation-модель) тут не участвует: она переживает
смену девайсов внутри записи, а auto-end слушает системный
`MicInUseProbe` (наш собственный tap там не виден) и срабатывает в обход
неё.

## Решение

Два слоя, оба TDD:

1. **Startup grace** (`MeetingRecorder.armAutoEnd`): auto-end не может
   финализировать запись моложе `autoEndStartupGraceSeconds = 30`.
   Release-таймер армится на `max(threshold, grace - currentElapsed())`;
   возраст — активное wall-clock время записи (паузы исключены).
2. **Тихий auto-reconnect** (`MeetingsCoordinator.handleDetectorEvent`):
   если детектор re-fire'ит в пределах
   `silentReconnectMaxGapSeconds = 15` после авто-энда — координатор
   возобновляет предыдущую запись сам через существующий
   `.reconnect`-путь (тот же recorder id/staging, маркер «Reconnected
   after N s» в транскрипте, пилюля сразу в `.recording`), без вопроса.
   Gap больше окна (но внутри grace 3 мин) — как раньше, пилюля
   «Notes | Reconnect | Skip». Если тихий рестарт recorder'а не удался —
   rollback уже восстановил `pendingReconnect`, показываем обычную
   reconnect-пилюлю (не оставляем юзера без записи и без пути назад).

Для тестируемости в координатор добавлен инжектируемый клок
`now: () -> Date` (дефолт `Date.init`).

## Почему

- Пилюля с выбором — правильный UX для осознанного «вышел и вернулся», и
  неправильный для аудио-турбулентности, которую пользователь не
  совершал. Порог 15 секунд разделяет эти два мира: джойн-флапы и смены
  девайсов укладываются в секунды, осознанный возврат — десятки секунд.
- Startup grace бьёт по корню конкретного инцидента (запись вообще не
  умерла бы), тихий reconnect закрывает класс целиком (флап может
  случиться и на 40-й минуте — например, смена аудио-девайса, при
  которой митинг-приложение переоткрывает микрофон дольше 3 секунд).
- Продуктовая рифма с требованием из PR #526: «смена устройств во время
  встречи — нормальный кейс, встреча не должна рестартовать или
  заканчиваться». Этот фикс продолжает то же требование для auto-end
  слоя.
- Тихий путь переиспользует пилюльный `.reconnect`-обработчик целиком
  (снапшот буфера, маркеры, откат при фейле) — ноль дублирования
  reconnect-механики.

## Что протестировали

- RED→GREEN: mic-release сразу после старта не финализирует запись в
  течение grace, но auto-end всё же срабатывает после его истечения
  (`test_auto_end_defers_until_startup_grace_elapses`).
- RED→GREEN: re-fire с gap ≈ 0 тихо возобновляет запись — тот же
  recorder id, пилюля в `.recording`, без `.suggestingReconnect`
  (`test_quick_rejoin_after_auto_end_resumes_recording_silently`).
- Регрессия: gap за окном (окно+5с через movable clock) по-прежнему даёт
  reconnect-пилюлю (`test_rejoin_past_silent_window_offers_previous_meeting_reconnect`).
- Фолбэк: без recorder factory тихий путь падает и показывает пилюлю,
  `pendingReconnect` жив (`test_silent_reconnect_falls_back_to_pill_when_recorder_cannot_start`).
- Полный сьют: 3898 тестов зелёные. Существующие auto-end тесты
  переведены на явный `autoEndStartupGraceSeconds: 0` там, где
  проверяется голый release-таймер.

## Отвергли

- Просто поднять `autoEndMicReleasedSeconds` (3с → 15-20с) — растягивает
  финализацию каждого реального конца встречи, а флап на середине записи
  всё равно не лечит.
- Только startup grace без тихого reconnect — не закрывает флапы после
  первых 30 секунд.
- Показывать индикатор «Reconnected» при тихом возобновлении — тихо
  значит тихо; маркер в транскрипте достаточен.
- Тихий reconnect для ручного Stop — не менялось: Stop финален по
  дизайну фичи (иначе кнопка Stop непредсказуема).
