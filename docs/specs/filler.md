# Spec: Filler (drop filler-word stripping)

## What we're building

**Filler** — пользовательский список слов-артефактов (filler words: «мм», «э-э», «ааа», «блин» и т.п.), которые детерминированно вырезаются из текста голосового дропа **перед вставкой**. Пользователь добавляет слова через chips-редактор в Dynamic Island (как у Vocabulary); при каждом дропе эти слова удаляются из готового транскрипта вместе с прилипшей пунктуацией, «красиво».

Filler — концептуальное зеркало Vocabulary:

- **Vocabulary** улучшает **вход** транскрипции — термины уходят в Soniox `context.terms` на backend, чтобы модель лучше распознавала нужные слова.
- **Filler** чистит **выход** — применяется целиком на клиенте как пост-процессинг готового текста. Список Filler **никогда не покидает устройство**.

Scope: только дроп (Option + /). Голос агента (R-Cmd) не затрагивается.

## Why this approach

- **Безопасность / приватность — главный драйвер.** Список Filler — это речевой профиль конкретного человека: его слова-паразиты, привычки, возможно мат и личные триггеры. Это чувствительные данные. Поскольку вырезание выполняется на клиенте (строковая операция над готовым текстом, не нужна модель), список **хранится только локально** и на сервер не отправляется вообще. Меньше PII у нас, меньше поверхность атаки. Это согласуется с линией пивота «мы вне data-path пользователя» — история дропов уже хранится только локально (SQLite `drop_entries`), Filler ложится туда же по философии.
- **Чисто клиентская фича, один репо, один PR.** Никаких изменений backend: ни миграции, ни endpoint, ни серверной валидации. ViewModel без сети — нет состояний loading/error, синхронный доступ к списку в hot-path дропа.
- **Детерминированность.** Пользователь добавил «блин» — оно гарантированно уберётся. LLM-cleanup в `smart`-режиме может пропускать конкретные слова и вообще отсутствует в `fast`-режиме (Soniox real-time без cleanup), поэтому именно в `fast` Filler особенно ценен.
- **Отдельный компонент, не обобщение vocab.** Vocab и Filler — разные по природе (vocab → API транскрипции, filler → пост-процессинг дропа). Обобщать рабочий vocab-код в параметризованный компонент не будем: разная семантика, и риск регрессии vocab не оправдан. Визуальный стиль chips можно **скопировать**, но сами vocab-компоненты не модифицируем.

## Key decisions

| Decision | Rationale |
|----------|-----------|
| Хранение списка — **локально** (UserDefaults, `FillerTermsStore`), `[String]` | Список не нужен серверу (применяется на клиенте). Локально = приватность + ноль backend-работы |
| Применение — клиент, `DropFillerFilter`, пост-процессинг после `process()`, перед `deliverDropTranscript()` | Готовый финальный текст чистится перед вставкой; одинаково для fast/smart |
| Модель — **только вырезание**, `[String]` | Названный сценарий — удаление артефактов. Замена X→Y не нужна (YAGNI) |
| Matching — **целые слова**, Unicode word-boundary, case-insensitive, точное слово | «мм» не должно калечить «программа»/«гамма». Регистр игнорируем (явное требование). Без fuzzy-растяжки («ааа» ≠ «аааааа») — отдельная история |
| Поддержка фраз | Term матчится буквально (слово или короткая фраза), целиком, по границам |
| Пунктуация — **умно + capitalize** | «вырезать красиво»: поглотить прилипшую запятую, схлопнуть пробелы, поднять регистр начала предложения |
| Scope — **только дроп** | Голос агента идёт в LLM (не вставляется как есть), модель сама игнорирует «мм» — ценность ниже, pipeline другой |
| UI — плашка **Filler** на освободившийся слот Integrations в Row 1 hover-панели | Слот свободен после пивот-демолишна; естественное место рядом с Vocab |
| Код — отдельные `FillerTermsViewModel` / редактор, vocab не трогаем | Разная семантика, защита рабочего vocab от регрессии |
| База — `feat/pivot-1b-client-demolition` | Там слот Integration уже удалён; Filler — изолированный PR без connect-claude багажа |
| Vocab → локально (local + ephemeral pass-through) | **Out of scope** этой работы. Отдельная спека (см. ниже) |

## Storage

`FillerTermsStore` — тонкая типобезопасная обёртка над `UserDefaults` (паттерн `UserPreferencesCache` / `PrivacyPreferences`).

- Ключ: `sidekey.replace.terms` (legacy key, preserved for backwards compatibility), значение — `[String]`.
- Синхронный `read()` / `write([String])`. Источник правды и кэш в одном — в hot-path дропа читается синхронно, отдельный кэш не нужен.
- Валидация (UX-границы, локальные): максимум 100 слов, ≤ 50 символов на слово, дедупликация без учёта регистра, без пустых/whitespace-only. (Зеркалируют vocab-правила для консистентности UX, но проверяются локально.)
- Durability: UserDefaults достаточно для списка слов. При полном сносе приложения список теряется — приемлемо; экспорт/импорт — возможное будущее.

## Cutting algorithm — `DropFillerFilter`

Чистый, изолированный, тестируемый тип. Контракт:

```
DropFillerFilter.apply(_ text: String, removing terms: [String]) -> String
```

Правила нормализации (после удаления вхождений):

1. Удалить каждое вхождение term как **целое слово** (Unicode word-boundary), **case-insensitive**. Терма экранируются как regex-литералы (учёт дефиса в «э-э», точек и т.п.). Эффективно — один проход объединённым паттерном `\b(term1|term2|…)\b`.
2. Поглотить прилипшую к слову запятую (типовой «, мм,» → одна запятая уходит).
3. Схлопнуть образовавшиеся двойные пробелы в один.
4. Убрать пробел перед пунктуацией `. , ! ? ; :`.
5. Trim ведущие/хвостовые пробелы и пунктуацию-сироту.
6. **Capitalize**: если вырезание оказалось в начале предложения (старт текста или сразу после `. ! ?`) — поднять регистр первой буквы следующего слова. Только первая буква; остальной регистр не трогаем (имена в середине не ломаем).

Edge cases — обязаны быть покрыты:
- Пустой список → текст без изменений (no-op).
- Term отсутствует в тексте → без изменений.
- Term как подстрока внутри слова → **не трогаем** («мм» в «программа»).
- Несколько разных terms; несколько вхождений одного term.
- Term с regex-спецсимволами / дефисом («э-э»).
- Множественные пробелы и переводы строк.
- Висячая `,;:` в конце после вырезания → убирается (`.`/`!`/`?` сохраняем — легитимные финалы / многоточие).

## Where it plugs in

Точные номера строк — verify при реализации (TDD); ниже — концептуальные точки на базе `feat/pivot-1b-client-demolition`.

- **`DropFillerFilter.swift`** (новый) — ядро вырезания.
- **`FillerTermsStore.swift`** (новый) — локальное хранилище + валидация.
- **`FillerTermsViewModel` + редактор-панель** (новые) — chips-UI, синхронно поверх store. Визуальный стиль chips копируем из `IslandVocabularyEditorPanel`; сам vocab-компонент не трогаем.
- **`IslandView.swift` / `IslandDropModeControl.swift`** — добавить плашку **Filler** в Row 1 hover-панели на слот, освободившийся после удаления Integrations; новый `IslandHoverPanelMode.fillerEditor` (по аналогии с `.vocabularyEditor`).
- **`AppDelegate.swift` drop pipeline** — вклинить `DropFillerFilter.apply(final, removing: store.read())` между `postProcessor.process(...)` и `deliverDropTranscript(...)`. **Два drop-пути** (около строк 1848–1857 и 2056–2070) — покрыть оба.
- **История дропов** — `dropHistoryRecorder.record(rawTranscript: raw, formattedText: cleaned, ...)`: в `formatted_text` пишем уже очищенный текст (то, что реально вставлено).

## Out of scope / Future work

- **Vocab → локально (local + ephemeral pass-through).** Отдельная спека и отдельный проект. Vocab нельзя полностью изолировать как Filler (транскрипция серверная, Soniox зовётся с backend по инварианту #2), поэтому «к пользователю» для vocab = убрать persistence: хранить локально, слать термины в `/api/transcribe` транзитом, backend прокидывает в Soniox и не сохраняет. Затрагивает оба репо + контракт transcribe + судьбу данных существующих юзеров + `transcription_mode`. Не блокирует Filler.
- **Fuzzy-растяжка** («ааа» ловит «аааааа») — возможное будущее, не в MVP.
- **Замена X→Y** — модель пар, не в MVP.
- **Экспорт/импорт списка** (кросс-девайс без backend) — при необходимости позже.
